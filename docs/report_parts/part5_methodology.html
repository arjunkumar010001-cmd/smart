CHAPTER 4
METHODOLOGY

This chapter details the implementation methodology for each of the six phases of Smart Hiring, including algorithms, mathematical formulations, data flows, and key design decisions.

4.1 Phase 1: Intelligent Job Posting

The Job Posting module transforms raw job descriptions into optimized, inclusive, and SEO-friendly listings using Large Language Models.

Workflow:

  1. Recruiter creates a job posting with title, description, required skills, experience level, and salary range.
  2. The JobOptimizerService sends the description to the Groq LLaMA-3.3-70B API via a structured prompt.
  3. The LLM returns: optimized description, suggested additional skills, inclusivity score (0–100), inclusivity suggestions (e.g., removing gendered language), SEO keywords, and readability notes.
  4. The recruiter reviews and accepts/modifies the suggestions before publishing.

AI Provider Waterfall:

Provider Selection Algorithm:
1. TRY Groq (LLaMA-3.3-70B-versatile)  — FREE, 500 req/day
   └─ IF available AND within daily limit → USE
2. TRY OpenAI (GPT-4o-mini)             — $0.15/1M tokens
   └─ IF API key configured AND within limit → USE
3. RETURN error "No AI providers available"

Key Features:

  • Inclusivity Analysis: Detects gendered language ("rockstar developer," "ninja"), age-biased terms ("young and dynamic"), and disability-exclusionary language ("must be able to stand for 8 hours").
  • SEO Optimization: Generates keywords that improve job visibility on search engines and job boards.
  • Skill Suggestion: Cross-references the job description against a skill ontology (250+ skills with aliases) to suggest commonly associated skills the recruiter may have overlooked.

4.2 Phase 2: Resume Refinery

The Resume Refinery is the core matching engine that ranks candidates against job requirements using a hybrid approach combining semantic embeddings and statistical methods.

Architecture:

Resume Processing Pipeline:

Resume (PDF/DOCX)
    │
    ▼
[Parser Layer]
    ├── PyPDF2 (PDF text extraction)
    ├── python-docx (DOCX text extraction)
    └── pdfplumber (complex PDF layouts)
    │
    ▼
[NLP Layer]
    ├── spaCy NER → Extract: names, emails, phones, organizations
    ├── Regex → Extract: years of experience, education, certifications
    └── Skill Ontology Mapper → Normalize skill names via aliases
    │
    ▼
[Matching Layer]
    ├── Primary: SBERT (all-MiniLM-L6-v2) → 384-dim embeddings → cosine similarity
    └── Fallback: TF-IDF (scikit-learn) → sparse vectors → cosine similarity
    │
    ▼
[Scoring Layer]
    ├── Semantic Score (40% weight)
    ├── Skill Match Score (30% weight)
    ├── Experience Score (15% weight)
    └── Certification/Project Score (15% weight)
    │
    ▼
Final Match Score (0–100%)

SBERT Semantic Matching Algorithm:

Given a job description J and a candidate resume R:

  1. Encode both into 384-dimensional vectors:
    vJ = SBERT(J) ∈ ℝ384
    vR = SBERT(R) ∈ ℝ384
  2. Compute cosine similarity:
    sim(J, R) = (vJ · vR) / (||vJ|| × ||vR||)
  3. Normalize to percentage: semantic_score = sim × 100

Skill Ontology Mapping:

The system maintains a skill ontology of 250+ skills organized into categories (programming_languages, frameworks, databases, cloud, devops, soft_skills). Each skill has a canonical name and a list of aliases. For example:

Canonical SkillAliases
JavaScriptjs, javascript, ecmascript, es6, es2015
Reactreactjs, react.js, react js, react native
Pythonpython3, python 3, py, cpython
Machine Learningml, deep learning, dl, artificial intelligence, ai

Composite Score Calculation:

FinalScore = 0.40 × SemanticScore + 0.30 × SkillScore + 0.15 × ExperienceScore + 0.15 × CertProjectScore

Where:

  • SemanticScore: SBERT cosine similarity × 100 (or TF-IDF fallback)
  • SkillScore: |matched_skills ∩ required_skills| / |required_skills| × 100
  • ExperienceScore: min(candidate_years / required_years, 1.0) × 100
  • CertProjectScore: Weighted count of relevant certifications and project keywords

Experience-Level Calibration:

The AI prompt system adjusts question complexity based on the intersection of difficulty level (easy/medium/hard) and experience level (fresher/mid/senior):

  • Fresher + Easy: Basic fundamentals, simple syntax (e.g., "reverse a string")
  • Fresher + Hard: Tricky edge cases, foundational (e.g., "handle integer overflow in palindrome check")
  • Senior + Easy: Straightforward real-world scenarios (e.g., "implement a basic LRU cache")
  • Senior + Hard: System design patterns, concurrency (e.g., "thread-safe producer-consumer with rate limiting")

4.3.2 Code Execution Sandbox

Candidate code is executed in isolated sandboxes via two API providers:

  • Piston API (Primary): Supports 60+ programming languages, 5-second timeout per execution, memory limits, no network access in sandbox.
  • Judge0 API (Fallback): Used when Piston is unavailable. Supports similar language coverage with configurable time/memory limits.

The Monaco Editor (version 0.44.0) provides a VS Code-like coding experience directly in the browser with syntax highlighting, auto-completion, and error indicators for 12+ programming languages.

Key Components:

  • AI Avatar "Alex": Animated CSS avatar with visual speech indicators (pulsing ring during TTS playback), providing a human-like interview experience.
  • Text-to-Speech (TTS): Web Speech API SpeechSynthesis reads questions aloud with configurable voice, rate (0.95), and pitch (1.0).
  • Speech-to-Text (STT): Web Speech API SpeechRecognition captures candidate responses with real-time transcription display. Falls back to text input if microphone is unavailable.
  • Dynamic Follow-up Questions: Based on the candidate's response quality, the AI generates contextual follow-up questions using Flan-T5 (google/flan-t5-base) or Groq API.
  • Video/Audio Recording: Records the entire interview session via MediaRecorder API (video/webm;codecs=vp9,opus), uploads to server at uploads/interview_recordings/, downloadable by both candidate and recruiter.
  • Anti-Malpractice: Tab-switch detection, face presence monitoring, and violation logging active throughout the interview.

Response Evaluation:

Each candidate response is evaluated by the AI service on multiple dimensions:

  • Technical Accuracy (40%): Correctness of technical concepts
  • Completeness (25%): Coverage of all relevant aspects
  • Communication (20%): Clarity and structure of explanation
  • Problem-Solving Approach (15%): Methodology and reasoning

4.8 Security and Anti-Cheating

Authentication & Authorization:

  • JWT Tokens: Flask-JWT-Extended with configurable expiry, stored in HTTP-only cookies or Authorization headers.
  • RBAC: Four roles — admin, company, recruiter, candidate — with decorator-based route protection.
  • Password Security: bcrypt hashing with 12 rounds via Flask-Bcrypt.
  • CORS: Configurable origins via Flask-CORS.
  • Rate Limiting: Per-IP and per-user rate limits on sensitive endpoints.

Assessment Security:

  • One active session per candidate per job (enforced server-side)
  • Session timeout with UTC timestamps (timezone-independent)
  • Server-side answer validation (answers cannot be modified after submission)
  • Violation logging with question context for post-assessment review
  • Blacklist enforcement: blacklisted candidates are blocked from starting assessments
  • Video recording evidence preserved on server for dispute resolution
